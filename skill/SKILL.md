# adytum

Хранилище секретов — git-репозиторий, где в рабочем дереве лежит
plaintext, а в git и на remote только шифротекст sops+age.

## Модель получателей

Получатели описаны в `.sops.yaml` и разложены по слотам ролей:

| Слот | Кто | Где видит |
|---|---|---|
| `age1REPLACE_ME_PC` | машина владельца | всё |
| `age1REPLACE_ME_APIARION` | VM apiarion | всё, кроме `personal/**` |
| `age1REPLACE_ME_RECOVERY` | recovery-машина | всё |

Правило `^personal[\\/]` — закрытый раздел: туда попадают только
владелец и recovery-машина. Остальное (`nova/**`, `comuki/**`) — по
общему правилу `^.*$`.

Приватные ключи лежат только локально в `~/.adytum/keys/<label>.txt`
(права 0600). В репозиторий они не попадают никогда.

## Разблокировка

Операции `get` и `run` заблокированы, пока нет маркера
`~/.adytum/unlocked`. Маркер живёт сутки: срок задаёт машина в
`~/.adytum/config` (`unlock_ttl`), а фоновый таймер обновляет его сам.

```
adytum unlock
```

Если инструмент вернул отказ с просьбой выполнить `adytum unlock` —
это запрос владельцу, а не повод искать обходной путь. Обходить
блокировку нельзя: она защищает от случайной утечки в лог агента.

Код возврата 2 означает «закрыто маркером разблокировки», код 1 —
обычную ошибку. Различие позволяет автоматике не искать обходной путь,
а ждать владельца.
## Команды

### Прочитать секрет

```
adytum get <project>/<service>            # весь файл
adytum get <project>/<service>.<KEY>      # одно значение
```

Проекты: `personal`, `nova`, `comuki`. Расширение определяется по
существующему файлу: `.env`, `.yaml`, `.yml`, `.json`.

Значение печатается в stdout и больше нигде не сохраняется.

### Запустить команду с секретами

```
adytum run --env <project>/<service> -- <команда> [аргументы...]
```

Ключи из env-файлов попадают в окружение процесса. Значения не
печатаются. Несколько `--env` можно указать подряд.

Команда выполняется через shell, поэтому `$ПЕРЕМЕННАЯ` в аргументах
раскрывается окружением. Это и есть контракт: агент пишет
`curl -H "Bearer $GITLAB_TOKEN" ...` и не видит значение секрета.

### Синхронизация

```
adytum sync              # получить изменения и отправить свои
adytum sync --pull-only  # только получить изменения
```

`git pull --rebase`, обновление рабочего дерева, `git push`. Режим
`--pull-only` ничего не отправляет — его использует таймер
автосинхронизации.

### Самопроверка

```
adytum doctor            # таблица проверок с подсказками
adytum doctor --json     # машинночитаемый отчёт
adytum doctor --role pc  # проверить как pc-машину
```

Проверяются инструменты, идентичность машины, git-фильтры, `.sops.yaml`,
remote, разблокировка, таймер и свежесть секретов. Каждая
непрошедшая проверка даёт строку с тем, что делать.

Doctor только проверяет — ничего не чинит. Проверки, неприменимые к
машине, помечаются как пропущенные: таймер systemd не нужен на
pc-машине, а его отсутствие — не поломка.

### Статус

```
adytum status
adytum status --json
```

Ветка, remote, получатели из `.sops.yaml`, состояние маркера
разблокировки, настроенные git-фильтры.

В JSON есть поля `locked` и `reason`: `locked` — закрыт ли доступ к
`get` и `run`, `reason` — `locked` (маркера нет или истёк) либо
`broken` (маркер есть, но нечитаем).

### Изменить секрет

```
adytum set <project>/<service> <KEY>       # одно значение
adytum set <project>/<service>             # все ключи записи
adytum set <project>/<service> <KEY> --stdin  # значение из stdin
adytum unset <project>/<service> <KEY>      # удалить ключ
adytum edit <project>/<service>            # открыть в $EDITOR
```

Значения вводит владелец: скрытым вводом или из stdin. В argv значение
не передаётся никогда — оно осталось бы в истории оболочки и в списке
процессов.

`edit` открывает файл в `$EDITOR` — это для неструктурированных
секретов (json, kubeconfig). Обычные ключи удобнее задавать через
`set`.

### Создать секрет

```
adytum new <project>/<service>
```

Создаёт файл из шаблона, запись в реестре и коммит.

## Доступ машин

### Выдать доступ

```
adytum grant <label>
```

Создаёт age-идентичность, кладёт приватный ключ в
`~/.adytum/keys/<label>.txt`, публичный ключ занимает слот роли в
`.sops.yaml`, файлы перешифровываются, изменения коммитятся и
отправляются.

Публичный ключ печатается один раз — передайте его машине получателя.

### Отозвать доступ

```
adytum revoke <label>
```

Убирает получателя из `.sops.yaml`, перешифровывает файлы, коммитит и
отправляет.

**Ротация обязательна.** Отзыв доступа не отменяет того, что машина
уже видела. Все значения, которые снятая машина успела прочитать,
нужно ротировать вручную.

## Профиль машины

Настройки машины лежат в `~/.adytum/config`:

```yaml
machine_scope:
  - personal
  - nova
role: pc            # pc | headless
pull_only: true     # машина только забирает изменения
unlock_ttl: 24h     # срок жизни маркера разблокировки
```

Роль определяет, какие проверки применимы: на `pc` таймер systemd не
нужен, на `headless` — нужен и без него реплика молча перестаёт
обновляться. Если файла нет, роль определяется по наличию `systemctl`.

## ДОНОТЫ

1. **Никогда не печатать значения секретов** в ответах, логах, коммитах
   и сообщениях об ошибках. В stdout попадает только то, что владелец
   запросил явно.
2. **Никогда не коммитить plaintext.** В репозиторий попадает только
   шифротекст: этим занимается clean-фильтр git. Не обходите фильтр
   (`git add --no-verify`, `git hash-object` в обход индекса).
3. **Приватные ключи в репозиторий не идут.** Файл идентичности age и
   приватный SSH-ключ — только в `~/.adytum/keys/` или `~/.ssh/`, с
   правами 0600. Machine identity остаётся локальным.
4. **Не читать `.env` и другие файлы секретов напрямую** — использовать
   `adytum get` или `adytum run`. Прямое чтение обходит разблокировку
   и контроль вывода.
5. **Не отключать разблокировку**, чтобы «проще было»: маркер защищает
   от утечки в лог агента.
6. **Не публиковать публичные ключи получателей как секрет.** Это
   публичные ключи age, их безопасность держится на приватной части.

## Ограничения

- CLI работает как обёртка над `sops`, `git` и `age`: эти бинарники
  должны стоять в PATH.
- На VM, где plaintext на диске запрещён, `get` и `run` не применяются:
  там только проверка, что секреты читаются через `adytum run`.
- `adytum sync` перезаписывает рабочее дерево (`git checkout -- .`),
  поэтому несохранённые правки секретов будут потеряны.
- Ключи с точками не поддерживаются: адрес вида `p/s.a.b` читается
  как имя файла `s.a.b` или как ключ `b` у сервиса `s.a`, и молча
  разбирать его опасно.
