# RUNBOOK: развёртывание adytum на новой машине

Пошаговая инструкция: от чистой машины до рабочего доступа к секретам.

## 0. Что нужно на машине

| Что | Зачем | Проверка |
|---|---|---|
| Go 1.22+ | сборка CLI (только при установке из исходников) | `go version` |
| `sops` | шифрование файлов | `sops --version` |
| `age` | генерация ключей (`age-keygen`) | `age-keygen --version` |
| `git` | хранение и синхронизация | `git --version` |

## 1. Установить CLI

Из исходников:

```bash
git clone https://github.com/lowern1ght/adytum
cd adytum
go build -o ~/.local/bin/adytum ./cmd/adytum
```

Через установочный скрипт (ставит зависимости, CLI и алиас `ady`):

```bash
bash skill/scripts/install.sh
```

Скрипт кладёт бинарник в `~/.local/bin` и создаёт рядом алиас `ady`,
который пробрасывает аргументы в `adytum`:

```bash
ady get personal/github
ady status
```

Убедитесь, что `~/.local/bin` в PATH:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

## 2. Получить материалы от владельца

Владелец выдаёт три вещи:

1. **Адрес приватного репозитория** (remote).
2. **Приватный ключ этой машины** — файл `~/.adytum/keys/<label>.txt`.
3. **Публичные ключи получателей** — они лежат в `.sops.yaml` и приезжают
   вместе с репозиторием.

Публичный ключ машины владелец выдаёт при `adytum grant <label>`.

## 3. Клонировать репозиторий

```bash
git clone <адрес remote> ~/adytum
cd ~/adytum
```

Репозиторий приватный: клонирование требует доступа к нему.

## 4. Положить приватный ключ

```bash
mkdir -p ~/.adytum/keys
cp <полученный файл> ~/.adytum/keys/<label>.txt
chmod 600 ~/.adytum/keys/<label>.txt
```

На Windows:

```powershell
New-Item -ItemType Directory -Force "$HOME\.adytum\keys"
Copy-Item <полученный файл> "$HOME\.adytum\keys\<label>.txt"
```

Проверьте права: ключ не должен быть доступен другим пользователям.

## 5. Указать идентичность машины

```bash
adytum identity <label>
```

Метка записывается в `~/.adytum/identity`. Через неё CLI находит
приватный ключ и передаёт его sops.

## 6. Инициализировать репозиторий

```bash
adytum init
```

Команда:

- проверяет наличие `sops` и `git`;
- создаёт `.gitattributes`, если его нет, и дописывает блок adytum в
  существующий;
- создаёт `.sops.yaml`, если его нет;
- подставляет публичные ключи вместо заглушек `age1REPLACE_ME_*`;
- настраивает git-фильтры `filter.adytum.clean`, `filter.adytum.smudge`,
  `filter.adytum.required` и diff-драйвер.

Проверьте результат:

```bash
adytum status
```

В выводе должны быть видны получатели и настроенные фильтры. Если
появилось предупреждение о незаполненных слотах — вернитесь к
владельцу: слот роли без ключа ломает шифрование целиком.

## 7. Синхронизироваться

```bash
adytum sync
```

Команда выполняет `git pull --rebase`, обновляет рабочее дерево
(`git checkout -- .`) — так smunge-фильтр применяется к изменённым
файлам — и отправляет локальные коммиты.

В рабочем дереве файлы остаются plaintext, в git — шифротекст:

```bash
head -1 personal/github.env        # plaintext
git show HEAD:personal/github.env  # шифротекст
```

## 8. Разблокировать операции

```bash
adytum unlock
```

Маркер `~/.adytum/unlocked` живёт 8 часов. Пока он есть, разрешены
`adytum get`, `adytum run` и инструменты плагина opencode.

## 9. Проверить доступ

```bash
adytum get personal/github
adytum run --env personal/github -- sh -c 'echo токен загружен'
```

Если `get` отвечает «срок разблокировки истёк» — выполните
`adytum unlock` ещё раз.

## 10. Установить плагин opencode

```bash
cp plugin/adytum.js ~/.config/opencode/plugins/adytum.js
```

Плагин добавляет инструменты `adytum_get` и `adytum_run`. Оба требуют
разблокировки: без маркера инструмент отвечает просьбой выполнить
`adytum unlock`.

## Вариант для VM

На VM, где plaintext на диске запрещён, схема другая:

1. **Не** ставьте `smudge`-дешифрование в рабочее дерево. Файлы в
   рабочем дереве остаются шифротекстом, а значения читаются через
   `adytum run`, который расшифровывает в памяти и отдаёт только
   переменные окружения.
2. Установите только CLI и зависимости (`sops`, `age`).
3. Положите приватный ключ в `~/.adytum/keys/<label>.txt` с правами
   0600.
4. Выполните `adytum identity <label>`.
5. **Не** выполняйте `adytum init` — он настраивает smunge-фильтр,
   который расшифрует файлы в рабочем дереве. Настройте фильтры
   вручную только для `clean`:

   ```bash
   git config filter.adytum.clean "sops encrypt --filename-override %f"
   git config filter.adytum.required true
   ```

   Рабочее дерево остаётся шифротекстом: `git checkout` не расшифровывает.
6. Проверьте, что в рабочем дереве шифротекст:

   ```bash
   head -1 personal/github.env
   ```

   Если видите `KEY=ENC[...]` — схема соблюдается.

7. `adytum unlock` на VM **не** включайте: агентские сессии там не
   должны читать значения секретов. Разблокировка живёт в
   `~/.adytum/unlocked` на конкретной машине, так что ПК и VM
   разблокируются независимо.

## Откат: отзыв доступа машины

Выполняется на машине владельца:

```bash
adytum revoke <label>
```

Команда убирает получателя из `.sops.yaml`, перешифровывает файлы
(clean-фильтр применяет новые правила ко всем файлам), коммитит и
отправляет изменения.

После этого на отозванной машине файлы перестают читаться: sops не
находит подходящего приватного ключа.

**Обязательный шаг после отзыва — ротация значений.** Отозванная
машина уже видела значения, и перешифровка этого не отменяет. Все
значения, которые машина успела прочитать, нужно заменить: пароли
сменить, токены перевыпустить, ключи перегенерировать.

## Обновление CLI

```bash
cd ~/adytum-tools
git pull
go build -o ~/.local/bin/adytum ./cmd/adytum
```

Обновление бинарника не трогает репозиторий секретов и не требует
повторного `adytum init`.
