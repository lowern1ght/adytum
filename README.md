# adytum

Персональный git-репозиторий секретов: в рабочем дереве — plaintext, в
git и на remote — только шифротекст `sops` + `age`.

Синхронизация между машинами обычная: `git pull` / `git push`.
Шифрование обеспечивают git-фильтры, которые настраивает `adytum init`.

## Зачем

Секреты разных машин лежат в одном месте и не разъезжаются: ПК, VM и
recovery-машина читают одну и ту же копию. Каждый видит только то, что
ему выдали: список получателей задан реестром `registry.yaml` (из него
генерируется `.sops.yaml`) и меняется только через `adytum grant` /
`adytum revoke`.

## Модель угроз

| Угроза | Что делает adytum |
|---|---|
| Remote утёк | В remote только шифротекст age; ключ age вне репозитория |
| Машина скомпрометирована | Видны только те секреты, которые этой машине выдали |
| Секрет попал в лог агента | `get` и `run` заблокированы без `adytum unlock` |
| Машина отозвана | `revoke` перешифровывает файлы; значения нужно ротировать вручную |
| Ключ попал в git | Приватные ключи живут только в `~/.adytum/keys/`, в git не попадают |

Чего adytum **не** делает: не защищает от утечки через саму машину
владельца, не отменяет компрометацию приватного ключа, не ротирует
значения сам.

## Требования

- Go 1.22+ (для сборки)
- `sops` — шифрование
- `age` — ключи (`age-keygen`)
- `git` с поддержкой фильтров

## Быстрый старт

### Новая машина

```bash
git clone <приватный remote> ~/adytum
cd ~/adytum
adytum init
adytum sync
```

`adytum init` проверяет `sops` и `git`, ставит git-фильтры, создаёт
`.gitattributes` и `.sops.yaml` (если их ещё нет) и подставляет в
`.sops.yaml` публичные ключи из `~/.adytum/recipients`.

Идентичность машины задаётся один раз:

```bash
adytum identity <label>
```

### Чтение секрета

```bash
adytum get personal/github              # весь файл
adytum get personal/github.GITHUB_TOKEN # одно значение
```

Тип секрета задаёт формат: `env` читается как dotenv, `yaml` и `json` —
по ключам верхнего уровня, `binary` и `kubeconfig` — целиком, без ключей.

### Реестр секретов

`registry.yaml` в корне хранилища описывает, какие секреты в нём есть,
какого они типа и кто их видит. Значений в реестре нет — только
описания.

```bash
adytum list                 # таблица записей
adytum list personal/github # подробно: описание, ключи, адрес ротации
adytum doctor               # сверка реестра, файлов и .sops.yaml
```

`.sops.yaml` генерируется из реестра командой `adytum reencrypt`, а не
редактируется руками: правила шифрования и описание доступа не должны
разъезжаться. Формат файла описан в [docs/REGISTRY.md](docs/REGISTRY.md).

### Запись секрета

```bash
adytum new personal/github --type env --description "GitHub PAT" --scope personal
adytum set personal/github GITHUB_TOKEN            # значение скрытым вводом
adytum set personal/github GITHUB_TOKEN --stdin    # значение из stdin
adytum unset personal/github GITHUB_TOKEN          # удалить ключ
adytum edit personal/github                        # открыть файл в $EDITOR
```

Значение не принимается из аргументов: оно осталось бы в истории
оболочки и в списке процессов. `adytum edit` нужен для неструктурированных
секретов — json, kubeconfig, бинарных файлов.

### Запуск команды с секретами

```bash
adytum run --env personal/github -- gh api /user
adytum run --env nova/gitlab -- curl -H "Bearer $GITLAB_TOKEN" ...
```

Ключи из env-файла попадают в окружение процесса; значения не
печатаются. Команда выполняется через shell, поэтому `$GITLAB_TOKEN` в
аргументах раскрывается окружением — агент не видит значение секрета.

### Синхронизация

```bash
adytum sync              # получить изменения и отправить свои
adytum sync --pull-only  # только получить изменения
```

Режим `--pull-only` ничего не отправляет: его использует таймер
автосинхронизации, чтобы фоновая задача не публиковала локальные
правки без участия человека.

Для приватного remote нужен доступ: он берётся из `~/.git-credentials`,
а если файла нет — из одноразового URL с токеном. Токен не попадает ни
в git config, ни на диск.

### Самопроверка

```bash
adytum doctor            # таблица проверок с подсказками
adytum doctor --json     # машинночитаемый отчёт
```

Проверяются инструменты (sops, age), идентичность машины, git-фильтры
вместе со скриптами, `.sops.yaml`, remote, маркер разблокировки,
таймер и свежесть секретов. Каждая непрошедшая проверка даёт строку
с тем, что делать.

### Развёртывание remote

```bash
adytum bootstrap-remote
```

Создаёт приватный репозиторий данных на GitHub (если его ещё нет),
настраивает `origin` и отправляет локальные коммиты. Токен берётся из
`~/.secrets/personal/github.env` (ключ `GITHUB_TOKEN`) или из
`~/.adytum/github-token` и используется только в памяти.

### Таймер автосинхронизации

```bash
adytum schedule
```

Ставит systemd-таймер (Linux), который раз в 5 минут выполняет
`adytum sync --pull-only`. На системах без systemd команда объясняет,
что планировщик нужно настроить вручную.

### Статус

```bash
adytum status
adytum status --json
```

Ветка, remote, получатели из `.sops.yaml`, состояние маркера
разблокировки, настроенные git-фильтры.

## Структура репозитория

```
.sops.yaml          правила шифрования: кому что доступно (генерируется из реестра)
registry.yaml       реестр секретов: типы, описания, scopes
.gitattributes      привязка git-фильтров к файлам секретов
personal/           закрытый раздел: владелец и recovery-машина
nova/               общий раздел
comuki/             общий раздел
```

Файл секрета лежит по пути `<project>/<service>.<ext>`, где `ext` —
`.env`, `.yaml`, `.yml` или `.json`.

## Получатели

Получатели описаны в реестре (`registry.yaml`) и разложены по scopes:

| Scope | Кто | Где видит |
|---|---|---|
| `personal` | машина владельца и recovery | `personal/**` |
| `default` | машина владельца, VM apiarion, recovery | всё остальное |

Закрытый раздел `personal/**` виден только владельцу и
recovery-машине. Остальное видно трём.

### Выдать доступ

```bash
adytum grant <label> [--scope <scope>]
```

Создаётся age-идентичность, приватный ключ кладётся в
`~/.adytum/keys/<label>.txt` (0600), публичный ключ попадает в раздел
`recipients` реестра, машина — в указанный scope (по умолчанию
`default`), `.sops.yaml` пересобирается из реестра, файлы
перешифровываются, изменения коммитятся и отправляются в remote.

Публичный ключ печатается один раз — передайте его машине
получателя вместе с приватным ключом.

### Отозвать доступ

```bash
adytum revoke <label>
```

Получатель убирается из реестра, `.sops.yaml` пересобирается, файлы
перешифровываются без него, изменения коммитятся и отправляются.

**После отзыва значения нужно ротировать вручную.** Отзыв доступа не
отменяет того, что машина уже прочитала.

## Как устроено шифрование

`adytum init` настраивает три git-фильтра:

```
filter.adytum.clean     "<~/.adytum/bin/adytum-clean.sh>" %f
filter.adytum.smudge    "<~/.adytum/bin/adytum-smudge.sh>" %f
filter.adytum.required  true
```

- **clean** — при `git add` plaintext шифруется, в индекс попадает
  шифротекст.
- **smudge** — при checkout шифротекст расшифровывается, в рабочем
  дереве снова plaintext.

Фильтры — не строки в git config, а скрипты-обёртки в `~/.adytum/bin`.
Причина в двух сбоях, которые ловили в бою:

- `sops encrypt` падает на пустом файле, и операция git ломается.
  Обёртка отдаёт пустой файл как есть.
- `sops decrypt` съедает stdin и падает, если машина не в списке
  получателей. Наивный `|| cat` даёт **пустой** файл — молчаливая
  потеря данных. Обёртка возвращает исходный шифротекст, и операция
  git проходит.

`--filename-override` обязателен: по нему sops определяет тип файла и
ищет `.sops.yaml`, а также выбирает правило `creation_rules` по пути.
Правило для закрытого раздела записано как `^personal[\\/]` — класс
символов покрывает и оба разделителя пути.

Файлы правил шифрования лежат в `~/.adytum/`:

```
~/.adytum/keys/<label>.txt    приватный ключ age (0600)
~/.adytum/identity             метка этой машины
~/.adytum/recipients           реестр «метка=публичный ключ»
~/.adytum/config               machine_scope: разделы, которые машина материализует
~/.adytum/unlocked             маркер разблокировки (8 часов)
~/.adytum/bin/                 скрипты git-фильтров
```

`machine_scope` ограничивает, что машина вообще видит: файлы вне
списка остаются в рабочем дереве шифротекстом. Список задаёт владелец,
`adytum init` подставляет его в smunge-фильтр.

## Разблокировка

`get` и `run` требуют активного маркера:

```bash
adytum unlock
```

Маркер живёт 8 часов. Он защищает от того, что агентская сессия
случайно выведет значение секрета в лог.

Без маркера `get` и `run` отказывают с подсказкой «попроси владельца:
adytum unlock». Ошибки CLI снабжены подсказкой следующего шага: без
неё агент обычно застревает на месте.

## Плагин opencode

`plugin/adytum.js` добавляет инструменты `adytum_get` и `adytum_run`.
Оба требуют разблокировки и отклоняются с просьбой выполнить
`adytum unlock`.

Установка:

```bash
cp plugin/adytum.js ~/.config/opencode/plugins/adytum.js
```

## Миграция старого хранилища

Старое plaintext-хранилище переносится в репозиторий разово:

```bash
adytum import ~/.secrets
```

Структура каталога сохраняется, файлы с расширениями `.env`, `.yaml`,
`.yml` и `.json` копируются в репозиторий и шифруются; остальные
пропускаются. Исходный каталог не изменяется.

После импорта опишите секреты в реестре (`adytum new` или правка
`registry.yaml` вручную) и пересоберите правила шифрования:
`adytum reencrypt`. Старое хранилище после этого удаляется.

## Разработка

```bash
go build ./...
go vet ./...
go test ./...
```

Юнит-тесты покрывают разбор env-файлов, реестр секретов, генерацию
`.sops.yaml` из scopes и запись ключей из stdin. Сеть и реальные
секреты в тестах не используются.

## Ограничения

- CLI — тонкая обёртка над `sops`, `git` и `age`: своей криптографии
  у него нет.
- `adytum sync` обновляет рабочее дерево через `git checkout -- .`:
  несохранённые правки секретов будут потеряны.
- На машине, где plaintext на диске запрещён, `get` и `run` не
  применяются — там остаётся только `adytum run` без вывода значений.
- `age`-ключи не имеют срока действия и не умеют отзываться сами:
  отзыв — это перешифровка файлов плюс ручная ротация значений.
